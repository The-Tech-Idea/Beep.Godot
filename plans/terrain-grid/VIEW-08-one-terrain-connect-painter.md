# VIEW-08 — One terrain-connect painter; windowed edits for the autotile bindings path

**Type:** duplication fix + enhancement (rule 3: one rule for "a run of cells becomes transition tiles, and we know it worked") · **Area:** `TerrainLibraryPainter`, `TerrainIsometricAutotileRendererComponent` (`RebuildSteps`, `PerformQueuedRebuild`, `OnCellChanged`), `TerrainTransitionLayerComponent` (`RefreshUsingTileSetTerrains`, terrain-set `OnCellChanged`), `TerrainTileRendererComponent` (`RebuildLibrary`, `PerformQueuedRebuild`, `_paintDiagnostics`) · **Status:** proposed 2026-09-15 · **Effort:** M (2–3 days) · **Risk:** medium (three painters converge on one; the autotile bindings path gains an incremental route it never had)

## Gap

Three places hand cells to Godot's `SetCellsTerrainConnect`, each with its own batching, draw order and verification (all read 2026-09-15):

1. `TerrainLibraryPainter.Build` (`TerrainLibraryPainter.cs:51-109`) — groups by terrain id in a `SortedDictionary` (`:61`), batches of 64 (`:79-86`), verifies every expected cell's `TileData.Terrain` and **throws** on a miss (`:87-93`), applies elevation alternatives (`:94-100`), erases outside the bounds (`:103`) and publishes by copying `TileMapData` onto the target (`:104-105`). `Update` (`:10-49`) is the windowed form: affected = changed cells + their valid neighbours (`:18-25`), a 2-cell context window (`:37`), a scratch `Build`, then only the affected tuples are copied (`:43-45`). It is generic in everything except its `TerrainLibraryPack` parameter (`pack.Projection` `:21`, `pack.Tiles`, `pack.TerrainBindings` `:68`, `pack.ElevationIndex()` `:60`).
2. `TerrainIsometricAutotileRendererComponent.RebuildSteps` bindings path (`TerrainIsometricAutotileRendererComponent.cs:381-505`) — groups in binding draw order (`:432-439`), batches of 64 into a hidden pending layer (`:465-471`), **counts** `missing` (`:478-484`), records `_paintDiagnostics` (`:486-492`), warns (`:493-494`), publishes by copying `TileMapData` (`:496-499`). Same shape as (1) with a different verification outcome and a different draw-order rule. The `UseTerrainConnections = false` branch (`PaintAssignedTiles`, `:544-576`) is a third per-cell painter inside the same method.
3. `TerrainTransitionLayerComponent.RefreshUsingTileSetTerrains` (`TerrainTransitionLayerComponent.cs:223-247`) — erases the bounds and issues **one unbatched** `SetCellsTerrainConnect` with `IgnoreEmptyTerrains` (`:246`) directly on the display layer, with **no verification**: a terrain set that cannot satisfy a cell leaves a silent hole where (2) would count `missing`. Reachable only with `UseTileSetTerrains = true`; the tile renderer's own layers set it false (`TerrainTileRendererComponent.cs:767-770`) and only `terrain_generation_layers_demo.tscn:65` turns it on.

Edits are windowed on exactly one of the three paths. The autotile **pack** path is incremental: `PerformQueuedRebuild` (`:167-197`) calls `TerrainLibraryPainter.Update` over `_libraryDirty` (`:179-180`). The autotile **bindings** path is not: `OnCellChanged` (`:233-241`) records the cell only when a pack is assigned (`:238`), so without one `PerformQueuedRebuild` falls to `:195` — `RequestRebuild()` (time-sliced) above 65 536 cells, else `Rebuild()` — a full repaint of every cell for a one-cell edit (10 240 cells on Huge). The transition layer's terrain-set branch does the same: `OnCellChanged` `:334` `if (UseTileSetTerrains) { RequestRefresh(); return; }` → a full `RefreshUsingTileSetTerrains` per edit (coalesced by `_refreshQueued`, `:121-131`), while its dual-grid branch repaints four display cells (`:335-342`).

Why it matters: a fix to the painter — batch size, elevation, the order two overlapping terrains are connected in — lands on whichever copy the reader opened. ENH-07's chunk-group patterns need "paint this window with a halo, verified" once, not three times. And the 2026-09-15 tile-view fix (`RecordBuildFailure`, retained display) had to be applied to two of the three painters by hand.

## Design

1. **One source description, two operations.** `TerrainConnectSource` (record in `TerrainLibraryPainter.cs`): `TileSet Tiles`, `int TerrainSet`, `TerrainProjection Projection` (neighbour validity, today `:21`), `bool UseConnections`, `bool IgnoreEmpty`, `Func<Vector2I, int?> TerrainAt` (null = no binding for the cell's kind), optional `Background` tuple (the pack's `-1` binding, `TerrainLibraryPack.cs:20-22`), optional `ElevationAt` + `ElevationIndex`. Built by `TerrainLibraryPack.ConnectSource(kindAt, elevationAt)` and by a `BindingsSource(bindings, Tiles, TerrainSet, UseTerrainConnections)` on the autotile renderer. `Build(target, source, bounds)` and `Update(target, source, bounds, changed)` keep their current bodies (`:51-109`, `:10-49`) but read the source instead of the pack.
2. **One batching and verification, `Connect`.** `Build` factors its middle into `Connect(pending, groups, drawOrder, source, expected, ConnectReport report)`: batches of 64 per terrain in the caller's draw order (packs enumerate ascending ids as today `:61`; bindings enumerate authoring order as today `:432-439` — the order is an input, the batching and the check are not), then fills `report.Missing` with every expected cell whose `TileData.Terrain` differs. `PaintAssignedTiles` (`:544-576`) moves into the painter as the `UseConnections == false` branch of `Connect` (same window-local `TerrainGeometry.HashInt` + `VariantSalt` selection, `:570-572`). Callers decide what a miss means, which is where they genuinely differ: `Build` for a pack throws (`:93`, the pack contract every library probe relies on); the autotile bindings path records `missing` in `_paintDiagnostics` and warns (`:486-494`); the transition layer **gains** the report — `MissingTransitionCells` and the same warning — and `TerrainTileRendererComponent.Rebuild` (`:303-311`) folds it into `_paintDiagnostics["valid"]`, which `TerrainWorldComponent.ActiveViewProblem()` already reads. That is the new count's consumer, in the same change.
3. **Callers.** `RebuildLibrarySteps` (`:507-542`) and `TerrainTileRendererComponent.RebuildLibrary` (`:334-335`) call `Build` with the pack source; the autotile bindings path (`:411-505`) becomes `Build` with `BindingsSource` on the pending layer plus diagnostics from the report; `RefreshUsingTileSetTerrains` (`:223-247`) becomes `Update(display, source, bounds.Grow(1), every bounds cell)` — through `Update` rather than `Build`, because the display may hold authored cells this layer does not own (`:195-198`) and `Update` copies only affected tuples.
4. **Windowed edits for the two paths that lack them.** Autotile: `_libraryDirty` becomes `_dirty`, filled unconditionally in `OnCellChanged` (`:238`); `PerformQueuedRebuild` gains a bindings branch mirroring the pack branch (`:170-194`): when the published bindings key (bindings array copy, `TerrainSet`, `Tiles` reference, `UseTerrainConnections`, bounds — the fields `BuildIsStale` compares, `:326-338`) still matches and no rebuild is in flight, `Update(_layer, BindingsSource, bounds, _dirty)`, `PublicationRevision++`, `LibraryCellsUpdated` reported; a miss → `RecordBuildFailure` and the display is retained (`:373-379`). Transition layer: the terrain-set branch of `OnCellChanged` (`:334`) collects dirty cells and runs `Update` on them in the same deferred callback the dual-grid branch uses (`:343-351`).
5. **Pin and docs.** `SetCellsTerrainConnect(` appears in `TerrainLibraryPainter.cs` only. Pages: `docs/terrain-engine/TerrainTransitionLayerComponent.md`, `TerrainIsometricAutotileRendererComponent.md`, `docs/game-builder/TERRAIN_LIBRARY_PACKS.md` (painter section).
