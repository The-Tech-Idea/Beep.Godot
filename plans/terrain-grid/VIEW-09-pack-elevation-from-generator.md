# VIEW-09 — Generator elevation reaches the LibraryPack views; one tier owner

**Type:** feature + duplication fix (D9: two elevation notions) · **Area:** `TerrainLibraryPack.Elevation.cs`, `TerrainLibraryEditSession.Elevation.cs`, `GridCellDataComponent.TerrainEdits.cs`, `TerrainLibraryPainter` (elevation callback), `TerrainIsometricAutotileRendererComponent` (elevated surface), `GridProjectionComponent` (`ElevatedTerrainPath`), `TerrainWorldComponent.Drawing.cs` (`BindGameplayGrid`) · **Status:** proposed 2026-09-15 · **Effort:** M (3 days) · **Risk:** medium (the editor's elevation brush changes what it writes; the grid binding gains a second elevated implementer)

## Gap

1. **A generated hill is flat in every pack view.** `TerrainLibraryPack.ElevationAt` (`TerrainLibraryPack.Elevation.cs:18-19`) answers only from the cell metadata key `terrain_library_elevation` (`ElevationProfileMetadata`, `:10`). Nothing maps the generator's `terrain_relief`/`terrain_elevation` to a profile, so `TerrainLibraryPainter.Build` asks `elevationAt(cell)`, gets `""`, and paints the base tile (`TerrainLibraryPainter.cs:96-99`) for every hill and mountain the generator placed. The pack's `ElevationValues` are validated as logical 0..1 heights (`:13`, `:77`) and every profile must cover every connection (`:94-101`) — the art is authored for exactly this and never receives generated relief.
2. **The key has one writer, the editor.** `PreviewTerrainElevation` (`GridCellDataComponent.TerrainEdits.cs:40-49`) writes `metadata[TerrainLibraryPack.ElevationProfileMetadata] = profile` and `terrain_elevation = elevation` (`:46-47`); `TerrainLibraryEditSession.PrepareElevationPaint` (`TerrainLibraryEditSession.Elevation.cs:9-38`) stages the tile bytes. That paint is invisible to every other reader of height: `terrain_relief` is untouched (`terrain_library_elevation_probe.gd:102` asserts it stays 1 while the profile becomes "quarter" and `terrain_elevation` becomes 0.2, `:100-101`), so the block view's tier (`TerrainLayers.LevelFor(terrain, relief)`, `TerrainLayers.cs:112-116`; `TerrainIsometricRendererComponent.SurfaceLevel` `:860-866`), navigation's height and the painter's shade all disagree with what the pack now draws. Three owners of one cell's height: relief, elevation, profile.
3. **The gameplay grid never sees a pack's rise.** `GridProjectionComponent.ElevatedTerrainPath` is typed `TerrainIsometricRendererComponent` (`GridProjectionComponent.cs:64`, `:80-90`; `CellToWorld` `:249-254` calls `terrain.SurfacePosition`). `BindGameplayGrid` binds the IsometricAutotile view as a flat `TileMapLayerPath` (`TerrainWorldComponent.Drawing.cs:253-261`), so a pack with `ElevationRisePixels` (`TerrainLibraryPack.cs:23`, validated `:64-65`) lifts its tiles while units, props and pickers keep the unraised diamond.

## Design

1. **Profiles by level.** `TerrainLibraryPack.ProfileForLevel(int level)`: profiles ranked ascending by `ElevationValues` (ties by id); `TerrainLayers.Ground` → `""` (base), `Hills` → rank 1, `Mountains` and `Summits` → the top rank (packs have no summit art; the block view's summit percentile is that view's realisation of one level — `TerrainLayers.cs:36-39`). A pack with a single profile maps Hills and Mountains to it (documented). `ElevationAt(cells, cell)` becomes `ProfileForLevel(TerrainLayers.LevelFor(kind, relief))` reading relief through `LiveTerrainSurfaceData.ReliefAtCell` (`ITerrainSurfaceData.cs:33-34`); the generator path reads `field.ReliefAtCell`. The tier rule stays where it is — `TerrainLayers.LevelFor` — and the pack only says which art realises a level.
2. **Delete the third owner.** `ElevationProfileMetadata` and the `terrain_library_elevation` key go. `PrepareElevationPaint` keeps staging bytes; the commit and `PreviewTerrainElevation` (`:40-49`) write `terrain_relief` (the chosen profile's level: base → `Ground`, rank 1 → `Hills`, top → `Mountains`; intermediate profiles → the nearest of those) and `terrain_elevation = ElevationValues[profile]` through `GridCellDataComponent.SetMetadata` — the same writer FEAT-05's `GridTerrainEditComponent` is designed on (`FEAT-05-terraforming-and-ramps.md`, design 1). ENH-02's classification already makes `terrain_relief` a `Navigation` change and `terrain_*` a `Terrain` change, so navigation, the block view, the painter and the data layers all see an elevation paint for the first time.
3. **One elevated-surface contract.** `ITerrainElevatedSurface` (`ecs/terrain/`): `SurfacePosition(cell)`, `SurfaceCorners(cell, Span<Vector2>)`, `SurfaceCellAt(position)`, `ContainsSurfaceCell(cell)`, `HasSurface`, signal `SurfaceRebuilt` — exactly the members the grid calls on the block view today (`:736-743`, `:775-789`, `:791-792`, `:812`, `:259`). The block view implements it as is. The autotile view implements it: `SurfacePosition = layer.Transform * (MapToLocal(cell) − (0, rise))` with `rise = ElevationRisePixels[ProfileForLevel(level)]`, corners = the diamond at the raised centre, `SurfaceCellAt` tries levels top-down as the block view does (`:780-787`), `SurfaceRebuilt` at publish (`TerrainIsometricAutotileRendererComponent.cs:499`, `:534`). `GridProjectionComponent` types `ElevatedTerrainPath`, `_cachedElevatedTerrain` and `_connectedTerrain` (`:64`, `:80`) to the interface. `BindGameplayGrid` (`:246-262`) binds the autotile view elevated when its pack has `ElevationRisePixels.Count > 0`, else flat as today. Consumers arrive with it: every companion placed through `CellToWorld` (VIEW-01) lands on the raised tile, and `TerrainCollisionComponent`'s `merge` (VIEW-02) reads `ElevatedTerrainPath.IsEmpty`.
4. `TerrainLibraryPack.Validate`/`RenderKey` are unchanged (`AppendElevationContract`, `TerrainLibraryPack.Elevation.cs:21-27`, still covers values and rises). `TerrainLibraryInspector`'s brush still picks a profile; only the commit changes.
5. Docs: `docs/game-builder/TERRAIN_LIBRARY_PACKS.md` (elevation section), `docs/terrain-engine/TerrainIsometricAutotileRendererComponent.md`, `docs/grid-system/GridProjectionComponent.md`.
