# GridBuildDefinition

Data model: a `[Tool][GlobalClass]` `Resource` describing one placeable build target (building, prop, or tool) in grid-builder games — identity, footprint, cost, and construction rules that a catalog lists and placement/build-site logic acts on. It is the addon's canonical [IGridSite](IGridSite.md): the three facts a player needs before commissioning a site — the ground it takes, the material it needs, and how long it takes **in turns** — read through [GridSitePorts](GridSitePorts.md) by the build toolbar's tooltip and by anything else that wants them without knowing this type by name.

Three of its fields carry deliberate, non-obvious distinctions the class doc comments spell out. `OccupiesCells` is kept separate from `BlocksNavigation` on purpose: the old code used `BlocksNavigation` for both, so any build that did not block pathing (a garden) could also be stacked without limit on the same cell, because nothing separately tracked footprint occupancy. `AllowedTerrainKinds`, when non-empty, overrides the placing scene's own allowed/blocked terrain policy entirely for *this* build only — an offshore platform can authorize `shallow_water` for itself without opening water placement to every other build that shares its scene. `Costs` and `RequiredMaterials` look similar (both read via `GridResourceAmount.Enumerate`) but mean different things: `Costs` is currency debited from a wallet the instant a build is confirmed, while `RequiredMaterials` is physical stock that must be hauled to the site by an `ITransporter` before its job is even dispatched — `GridBuildSiteComponent` is what turns that second field into a wait state. The type also supports two authoring shapes uniformly: a plain `Godot.Collections.Dictionary` (PascalCase or snake_case keys) or a `Resource` (a typed `GridBuildDefinition` or any duck-typed resource with matching property names), both parsed through the same shared `GridDefinitionReader` helpers, so a catalog can mix inline dictionary entries and `.tres` assets.

## Public API
- `[Export] string BuildId = "workshop"` — the only identity field; empty/whitespace makes `TryRead` reject the entry.
- `[Export] string DisplayName`, `Category = "Buildings"` — menu labels/grouping.
- `[Export] PackedScene? Scene`, `Texture2D? PreviewTexture` — at least one is required for `HasPlayableSurface()` to pass.
- `[Export] Vector2I Footprint = Vector2I.One` — raw footprint size; see `EffectiveFootprint`.
- `[Export(Range 0..600)] int BuildTurns = 0` — turns of work the build takes. A turn is a day, so the same number means five end-turns in a turn-based game and five in-game days in a real-time one. Zero means the build has no construction phase and is simply placed (the default — a definition opts *into* construction by declaring turns). Replaced `BuildSeconds`, which was only correct on the real-time axis.
- `[Export] string JobKind = "build"` — job-kind string a worker/builder matches against.
- `[Export] bool BlocksNavigation = true` — whether the placed build blocks pathing.
- `[Export] bool OccupiesCells = true` — whether placement treats the footprint as occupied (separate from `BlocksNavigation`; see class comment above).
- `[Export] bool SetZIndexFromY = true` — whether the placed node's Z-index is derived from its Y position.
- `[Export] Godot.Collections.Array<string> AllowedTerrainKinds` — non-empty overrides the placing scene's terrain policy for this build alone; empty defers to the scene.
- `[Export] Godot.Collections.Array Costs` — wallet-debited resource costs, read via `GridResourceAmount.Enumerate`.
- `[Export] Godot.Collections.Array RequiredMaterials` — physically delivered stock a `GridStorageComponent` on the placed node must hold before the build job is created.
- `[Export] Godot.Collections.Array<PackedScene> ConstructionStages` — optional construction-site scenes (`GridBuildStageVisualComponent`); empty means the feature is unused for that build. Each is told the site's footprint, cell size, state, materials, progress and work hits through `IConstructionVisual`, so one scene serves any build size — the shipped `wood_/steel_/brick_construction_site.tscn` (all `construction_stage.gd`) is listed ONCE and draws the whole site from `BuildProgress`, tiling material swatches to whatever `Footprint` the build has. Several scenes listed are shown by progress band instead, for a project with static per-stage art. Nothing here says how big the art was drawn; that is the scene's own knowledge. A build with stages has its placed node hidden until completion (`GridBuildSiteComponent`).
- `public Vector2I EffectiveFootprint` — `Footprint` with each axis clamped to a minimum of 1.
- `public int EffectiveBuildTurns` — `BuildTurns` clamped to `>= 0`.
- `Vector2I SiteFootprint`, `Godot.Collections.Array SiteMaterials`, `int SiteTurns` — the `IGridSite` contract, mapped to `EffectiveFootprint`, `RequiredMaterials` and `EffectiveBuildTurns`. `Costs` is deliberately *not* a site fact: it is wallet currency, not material that arrives at the site.
- `public bool HasPlayableSurface()` — `true` if `Scene` or `PreviewTexture` is set.
- `public static IEnumerable<GridBuildDefinition> Enumerate(Godot.Collections.Array builds)` — yields a definition per entry via `TryRead`, silently skipping unparseable entries.
- `public static bool TryRead(Variant entry, out GridBuildDefinition? definition)` — parses a `Dictionary` (dual-key PascalCase/snake_case) or a `Resource` entry (returns an already-typed `GridBuildDefinition` by reference as-is; reflects field-by-field off any other `Resource`); returns `false` unless the resulting `BuildId` is non-blank.

## Dependencies
- Parsing is delegated entirely to `GridDefinitionReader` (`using static Beep.ECS.GridDefinitionReader;`) for both the dictionary and reflected-resource read paths.
- `GridBuildCatalogComponent` iterates `GridBuildDefinition.Enumerate(Builds)` for every lookup/listing method it exposes; `GridBuildSiteComponent` reads `EffectiveBuildTurns`, `RequiredMaterials`, `JobKind`, and `Costs` off definitions it fetches from the catalog, and hands the turns to `GridJobQueueComponent.AddJob` as the job's work amount — the queue is unit-agnostic, and `GridWorkClockComponent` is what makes that number mean turns. `GridBuildStageVisualComponent` reads `ConstructionStages`. (There is no separate builder-agent type any more — a build's job is claimed and completed by any `GridWorkerComponent`/`IWorker` with its `JobKind` allowed, the same as any other job kind; see `IWorker`.)

## Notes
- The `Dictionary` and `Resource` branches of `TryRead` each independently list the same ~13 fields rather than sharing one field-list; only the per-field reads (`ReadString`, `ReadObject`, etc.) are shared through `GridDefinitionReader`, so adding a new exported field means editing both branches.
- When `entry` is already a `GridBuildDefinition` resource, `TryRead` hands back the *same instance* rather than reflecting a copy — callers get a live reference to the original asset in that case, but a freshly-allocated `GridBuildDefinition` in the dictionary and duck-typed-resource cases. Code that mutates a definition it got from `Enumerate` could therefore be mutating a shared `.tres` asset or a throwaway copy depending on how that particular entry was authored.
