# GridObjectiveEventBinderComponent

A `[Tool][GlobalClass]` `Node` that wires grid gameplay signals — completed jobs, finished builds, gathered resources, completed production cycles — into `GridObjectiveTrackerComponent` progress calls, so a project doesn't need bespoke glue code connecting its job/build/resource/production systems to its objective system.

Its class comment states the purpose plainly: "Connects grid gameplay signals to GridObjectiveTrackerComponent progress... without project-specific glue." The design follows the same shape as the objective definitions it feeds: every source event is turned into a normalized objective id via a per-category configurable prefix (`CompletedJobPrefix`, `CompletedBuildPrefix`, `GatheredResourcePrefix`, `CompletedProductionPrefix`) plus `GridObjectiveDefinition.Normalize`, so a game can define `build_house` or `gather_wood` objectives just by matching the prefix+id convention rather than writing per-objective signal handlers. Four independent boolean toggles (`TrackCompletedJobs`, `TrackCompletedBuilds`, `TrackGatheredResources`, `TrackCompletedProduction`) let a scene opt out of any category, and resource/production sources are discovered by recursive tree walk (`ConnectResourceNodes`/`ConnectProductionNodes`) rather than requiring every node to be pre-registered, since a settlement can spawn resource nodes and production buildings dynamically.

## Public API
- `[Signal] ObjectiveEventAppliedEventHandler(string objectiveId, int amount, string source)` — emitted after `ApplyObjectiveEvent` successfully applies progress; `source` is a fixed tag (`"job_completed"`, `"build_completed"`, `"resource_gathered"`, `"production_completed"`, or `"manual"`) identifying which path triggered it.
- `NodePath ObjectiveTrackerPath / JobQueuePath / BuildSitePath / ResourceNodesRootPath / ProductionRootPath { get; set; }` — wiring for the tracker and the four optional signal sources; when a path is empty, the corresponding tracker/job-queue/build-site is instead located via `EntityComponent.FindComponent<T>` against the current scene (resource/production roots have no such fallback — they stay null if unset).
- `bool AutoConnect { get; set; } = true` — if true and not running in the editor, `_Ready` calls `ConnectSystems()` automatically.
- `bool TrackCompletedJobs/TrackCompletedBuilds/TrackGatheredResources/TrackCompletedProduction { get; set; } = true` — per-category enable switches.
- `bool UseGatherAmountAsProgress { get; set; } = true` — if true, a resource-gathered event's `amount` becomes the progress delta; if false, every gather event counts as 1 regardless of amount.
- `string CompletedJobPrefix { get; set; } = ""` / `CompletedBuildPrefix { get; set; } = "build_"` / `GatheredResourcePrefix { get; set; } = "gather_"` / `CompletedProductionPrefix { get; set; } = "produce_"` — prefixes prepended to the normalized source id to form the objective id.
- `void ConnectSystems()` — resolves references, prunes stale tracked nodes, and connects whichever signal sources are enabled and available; idempotent per source (`_jobsConnected`/`_buildSitesConnected` flags, and resource/production nodes are tracked in `HashSet`s so a node is never double-subscribed).
- `void DisconnectSystems()` — unsubscribes every currently connected signal, guarding each with `GodotObject.IsInstanceValid` before unsubscribing, then clears connection state and the tracked-node sets. Called from `_ExitTree`.
- `bool ApplyObjectiveEvent(string objectiveId, int amount = 1, string source = "manual")` — normalizes `objectiveId`, calls `_tracker.AddProgress(id, Mathf.Max(1, amount))`, and on success emits `ObjectiveEventApplied`. Returns `false` if the tracker isn't resolved, the id normalizes to empty, or the tracker rejects the progress call (e.g. objective inactive or already complete).
- `string ObjectiveIdForJob(string jobKind)` / `ObjectiveIdForBuild(string buildId)` / `ObjectiveIdForResource(string resourceId)` / `ObjectiveIdForProduction(string recipeId)` — build a prefixed, normalized objective id for each category; usable directly by callers that want to predict an id without triggering an event.

## Dependencies
- Resolves and calls into `GridObjectiveTrackerComponent.AddProgress(string, int)` (defined in this same batch, `GridObjectiveTrackerComponent.cs`) — this is the only write path this component has into the tracker.
- Resolves and subscribes to `GridJobQueueComponent.JobCompleted` and calls `GridJobQueueComponent.GetJobKind(jobId)` (outside this batch).
- Resolves and subscribes to `GridBuildSiteComponent.BuildSiteCompleted` (outside this batch).
- Recursively finds and subscribes to `GridResourceNodeComponent.Gathered` and `GridProductionComponent.ProductionCompleted` under `ResourceNodesRootPath`/`ProductionRootPath` (outside this batch).
- Uses `GridObjectiveDefinition.Normalize` (this batch, `GridObjectiveDefinition.cs`) in every `ObjectiveIdFor*` method.
- Uses `EntityComponent.FindComponent<T>(Node)` (outside this batch) as the path-not-set fallback for the tracker, job queue, and build site.
- Not established from this batch alone: no other file in this batch calls into `GridObjectiveEventBinderComponent` — it appears to be a leaf orchestrator wired directly from a scene, not something the tracker, definition, or calendar files reference back.

## Notes
- `OnJobCompleted` calls `_jobs.GetJobKind(jobId)` but does not null-check or otherwise validate the returned kind before normalizing and prefixing it — if `GetJobKind` can return an empty string for an unknown job id, that would still form a syntactically valid (if empty-suffixed) objective id like `""` normalized further downstream by `ApplyObjectiveEvent`, which does guard against a blank normalized id, so this fails safe rather than silently.
- `ResolveReferences` re-resolves `_tracker` via `EntityComponent.FindComponent` on every call when `ObjectiveTrackerPath` is empty and `_tracker` is currently null/invalid, but does not cache a "not found" result — on a scene where no tracker exists yet, every `ApplyObjectiveEvent` call pays a full scene-tree search. This mirrors the same NodePath-or-scene-search resolution pattern used by `GridCalendarComponent` in this batch (`ResolveReferences` there does the analogous thing for `GridCellDataComponent`), so it's a consistent house style rather than an isolated oddity.
- `PruneInvalidTrackedNodes` is called from `ConnectSystems` but not from `DisconnectSystems` — `DisconnectSystems` already null/valid-guards each unsubscribe individually, so this isn't a bug, just an asymmetry between the two methods' cleanup strategy.
