# GridTransportChainComponent

A standing transport chain between ports — the general mechanism a pipeline is one dress for. Authored as an ordered `NodePath` list (`Chain`): first the source (an extractor's buffer, a tank), any number of intermediate links (tanks, buffers, even parked transporters — every `ITransporter` is both ports), last the sink. Every tick, material moves one link along at `FlowRatePerTurn`, each hop using the same safe hand-off (`GridPorts.Transfer`) the whole logistics layer uses. A crude pipeline, a conveyor line, a train of cars, a bucket brigade of boats are all meant to be the same component with different links and a different rate — not separate systems.

The chain carries whatever its links actually *hold* — it asks each port via `StoredIds()` instead of being told what it carries; restricting it to a single resource (a "crude pipeline") is the developer's authoring choice via the `ResourceIds` filter, never a rule the component enforces itself. Backpressure is the deliberate design, not an accident: the doc comment is explicit that material moves from the *sink end backward* each tick, so each link only advances into the space the link ahead of it just freed. When the last port is full, the whole chain stops — buffers hold what they hold, the source stops being drained (a buffered extractor stalls with its deposit intact), and `ChainBlocked` reports it; `ChainUnblocked` fires when the sink drains and flow resumes. Nothing is ever pushed into a full port and nothing is lost.

## Public API
- `bool IsBlocked { get; }` — true while the sink has no free space and material is waiting behind it.
- `void AdvanceWork(float turns)` — advances the chain by up to `FlowRatePerTurn * turns` units (accumulated in `_flowBudget`, spent whether or not anything actually moves — a stalled chain cannot bank an unbounded burst for the moment the sink drains). Bound to `GridWorkClockComponent.WorkTick` (found via `WorkClockPath`, or scene-wide when it is empty), so a chain moves the same amount of material per in-game day on either time axis; with no work clock anywhere it self-ticks from `_Process` at one turn per second.
- `void Tick(double delta)` — the old entry point, kept: converts a frame delta to turns and calls `AdvanceWork`, for direct/orchestrated driving.
- `protected virtual int MoveLink(Node from, Node to, string resourceId, int amount)` — HOOK: one hand-off along the chain. Default calls `GridPorts.Transfer`; override for leaks, per-link filters, or in-transit processing.
- Exports: `ResourceIds` (`Array<string>`, empty = carries anything the links hold), `Chain` (`Array<NodePath>`, source first, sink last, ≥2 entries required), `FlowRatePerTurn`, `WorkClockPath`.
- Signals: `Flowed(string resourceId, int amountIntoSink)`, `ChainBlocked(string resourceId)`, `ChainUnblocked(string resourceId)`.

## Dependencies
- Resolves every entry in `Chain` fresh each advance via `ResolveLinks()` (`GetNodeOrNull<Node>`, discarding invalid/freed nodes) — the only component in this batch that re-resolves its entire wiring every tick rather than caching and revalidating with `IsInstanceValid`.
- Calls `GridPorts.Transfer` (outside this batch) as its default link hand-off, and `GridPorts.FreeSpace`/`GridPorts.StoredIdsOf` (outside this batch) to detect a full sink and to enumerate what a link can offer.
- Duck-types each link node via `HasMethod("Stored")` and `Call("Stored", id)` directly (not through `GridPorts`) inside `CarriableIds`, alongside the `GridPorts.StoredIdsOf` call for `StoredIds()` — two different duck-typed reads on the same node in one method.
- Not established from this batch alone whether anything constructs or drives a `GridTransportChainComponent` from code; it appears to be scene-authored (a `NodePath` list set up in the editor) with no manager registering it, unlike the extraction/transport managers.

## Notes
- Iteration order in `AdvanceWork` is `for (int i = _links.Count - 2; i >= 0; i--)` — sink-to-source — which is exactly what implements the stated backpressure design; the code matches the doc comment's explanation.
- The blockage detection scans from the *front* (`for (int i = 0; i < _links.Count - 1 ...)`) to find the first `blockedId`, after the sink-to-source move loop already ran — meaning `blockedId` is only computed when nothing reached the sink in that tick at all, not per-link.
- `CarriableIds` treats a link that lacks a `Stored(string)` method (`canAskAmount == false`) as always offering everything `StoredIds()` reports, with no amount check — a minimal duck-typed link that implements only `StoredIds`/`Unload`/`Load` (skipping `Stored`) can be offered for a move even though the code can't confirm it holds anything; `MoveLink`/`GridPorts.Transfer` would then simply move 0 if `Unload` genuinely has nothing, so this degrades safely rather than duplicating anything.
- No `ISaveable` implementation and no `SaveKey` — unlike `GridStorageComponent`, `GridSubsurfaceStoreComponent`, and `GridProspectingComponent` in this batch, chain flow state (`_flowBudget`, `IsBlocked`) does not round-trip through a save; only the material actually sitting in the linked ports (which do save, individually) persists.
