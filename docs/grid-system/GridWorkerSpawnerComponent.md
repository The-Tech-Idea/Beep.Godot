# GridWorkerSpawnerComponent

`GridWorkerSpawnerComponent` is the factory for worker/truck/NPC units: given a cell, it validates the spawn is legal (in bounds, unblocked, unoccupied, on allowed terrain), instantiates a unit (a custom `PackedScene` or a built-in placeholder `CharacterBody2D`), ensures it has both a `GridPathFollowerComponent` and a `GridWorkerComponent`, and wires every NodePath those two components need to function — grid, navigation, job queue — before handing the finished unit back. The class doc comment states its job in one line: "Spawns worker, truck, or NPC units from a base/building and wires them to the reusable grid navigation and job systems."

It exists so that "spawn a worker" is one call instead of a multi-step recipe every project would otherwise repeat: instantiate, add a path follower, add a worker component, and cross-wire four or five NodePaths between them and the shared grid systems. `EnsurePathFollower`/`EnsureWorker` look for pre-existing components on the instantiated node before creating new ones, so a custom `UnitScene` that already carries a correctly configured follower/worker is respected rather than duplicated — this is what lets a project swap in real art and behavior while still getting the spawner's wiring and validation for free.

## Public API
- `Node2D? SpawnWorker()` / `Node2D? SpawnWorker(Vector2I cell)` — validates, instantiates, wires, and returns the new unit, or returns null and emits `SpawnRejected(reason)` on failure (`"missing_grid_navigation_or_jobs"`, `"missing_units_root"`, `"max_workers_reached"`, a terrain/occupancy reason from `SpawnBlockReason`, `"unit_scene_must_instantiate_node2d"`, or — when the instantiated unit carries an `ActorComponent` — `"missing_actor_registry_or_owner"` and `"missing_actor_definition"`, both of which free the half-built unit before rejecting). The no-argument form spawns at `SpawnCell`, unless `SpawnAtStartArea` is on (see below).
- Start-area spawning (FEAT-09): with `SpawnAtStartArea` on, `SpawnWorker()` asks the `StartAreaPath` component for `SpawnCellsFor(<this spawner's start>, int.MaxValue)` (every walkable cell of that start's area, nearest the origin first) and takes the first one that no live spawned unit stands on and that passes `SpawnBlockReason`, then spawns there through `SpawnWorker(cell)`. It rejects with `"missing_start_area_or_grid"` when the start-area component or grid does not resolve, with `"owner_has_no_start"` when this spawner's owner is a real player whose faction was assigned nothing, and with `"no_start_area_spawn_cell"` when no cell qualifies. Successive workers therefore take successive cells instead of stacking. `AutoSpawnOnReady` spawns its initial workers the same way when the flag is on, and at `SpawnCell + (i, 0)` when it is off. `SpawnWorker(Vector2I cell)` is unchanged.
- Whose start (FEAT-10): `StartIndexForOwner()` *(private)* resolves **this spawner's own owner**, not this machine's player, so a map with a spawner per player puts each player's units in their own area from one scene. The chain is `OwnerId → ActorRegistryComponent.FindPlayer(OwnerId) → PlayerContextComponent.FactionId → GridStartAreaComponent.StartIndexOf(...)`. It falls through to the start component's `ActiveStartIndex` at three points — the start component has no `FactionCatalog`, `OwnerId` is empty, or the registry does not resolve or does not know that player — because a single-player sandbox has one player and one start, and that is what it means. It answers `-1`, and the spawn is refused as `owner_has_no_start`, only when the owner *is* a registered player whose faction holds no start: refusing is the honest answer, because every other area belongs to somebody else. Before this it read `ActiveStartIndex` directly, which would have put every player's units in the local player's area.
- `Array<Node> GetSpawnedUnits()` — the live, freed-unit-pruned list of everything this spawner has produced.
- `bool CanSpawnAt(Vector2I cell)` — dry-run predicate mirroring `SpawnWorker`'s validation without side effects.
- `int SpawnedCount` — prunes freed units, then returns the count.
- `int EffectiveMaxWorkers`, `int EffectiveInitialWorkers`, `float EffectiveDefaultUnitSpeed` — sanitized versions of the corresponding exports.
- Signals: `UnitSpawned(unit, workerId, x, y)`, `SpawnRejected(reason)`.
- Exports: `UnitScene`, `UnitDefinition` (an `ActorDefinition`; its own `Scene` wins over `UnitScene`), `OwnerId` (the player this spawner's units belong to — stamped on every spawned actor, and since FEAT-10 the input to `StartIndexForOwner`), `ActorRegistryPath`, `UnitsRootPath`, `GridPath`, `NavigationPath`, `JobQueuePath`, `CellDataPath`, `PlacementPath`, `SpawnCell`, `SpawnAtStartArea` (default off), `StartAreaPath` (a `GridStartAreaComponent`; `_GetConfigurationWarnings()` warns when `SpawnAtStartArea` is on and it is empty), `WorkerIdPrefix`, `AutoSpawnOnReady`, `InitialWorkers`, `MaxWorkers`, `DefaultUnitSpeed`, `DriveCharacterBody`, `SetZIndexFromY`, `TreatCellDataBlockedAsUnspawnable` (default on), `TreatBlockedTerrainKindsAsUnspawnable` (default on), `TreatPlacementOccupiedAsUnspawnable` (default on), `BlockedTerrainKinds` (defaults to `GridTerrainRules.DefaultBlockedTerrainKinds()`), `AllowedTerrainKinds`.

## Dependencies

- Resolves `GridProjectionComponent`, `GridNavigationComponent`, `GridCellDataComponent`, `GridPlacementComponent` (all outside this batch) to validate and place a spawn.
- Resolves `GridStartAreaComponent` through `StartAreaPath` and reads `FactionCatalog` (only as the "does this map have factions at all" test), `StartIndexOf`, `ActiveStartIndex` and `SpawnCellsFor` when `SpawnAtStartArea` is on; `GridProjectionComponent.WorldToCell` gives each live spawned unit's standing cell. It never resolves a `GridFactionCatalog` itself and never asks the catalog for a colour or an index — the start component owns that resolution.
- Resolves `ActorRegistryComponent` through `ActorRegistryPath` with a plain `GetNodeOrNull` (no scene-wide fallback and no caching) in two places: `StartIndexForOwner`, to turn `OwnerId` into a `PlayerContextComponent.FactionId`, and the actor-stamping branch of `SpawnWorker(cell)`.
- Creates and configures `GridPathFollowerComponent` (outside this batch) and `GridWorkerComponent` (this batch) on every spawned unit — this is the file that sets `worker.JobQueuePath`, `worker.GridPath`, `worker.PathFollowerPath`, and `worker.WorkerId` via `GetPathTo`, which `GridWorkerComponent.ResolveReferences()` later reads back.
- Resolves its own `GridJobQueueComponent` (this batch) purely to hand its path to each spawned worker and as a precondition for spawning at all (`_jobs == null` rejects the spawn).
- Uses `GridTerrainRules.Normalize`/`IsAllowed`/`MatchesAny`/`DefaultBlockedTerrainKinds` (outside this batch) for terrain-kind eligibility.
- `GridDispatchBoardComponent` (this batch) subscribes to this spawner's `UnitSpawned`/`SpawnRejected` purely for status text and an arrival animation, without using it to actually create its own dispatched vehicle — established within this batch.

## Notes

- The terrain-kind normalization comment is a documented bug fix, not speculation: "`GridTerrainRules.Normalize` also replaces spaces and dashes — the private normalizer this replaced had quietly forgotten that, so this component alone treated 'Deep Water' and 'deep_water' as different kinds." Centralizing normalization in `GridTerrainRules` retired a second, divergent copy of the same logic.
- `CreateUnitNode`'s placeholder (a blue diamond `Polygon2D` on a `CharacterBody2D` with a `RectangleShape2D` collider) is real runtime behavior when `UnitScene` is unset, not test-only sample data — a project with no authored unit art still gets a spawnable, visible, collidable unit.
- `UniqueUnitName` appends `_2`, `_3`, … on a name collision under `_unitsRoot` rather than rejecting the spawn.
- `SpawnBlockReason` checks navigation bounds/blocked, then placement occupancy, then (only if `_cellData` is resolved) cell-data blocked flag and terrain-kind eligibility — so a scene with no `GridCellDataComponent` wired simply skips terrain-kind filtering entirely rather than failing closed.
- `StartIndexForOwner` is called *after* the standing-unit set is built and after the start-area/grid null check, so `owner_has_no_start` is the second refusal a start-area spawn can give, not the first. `_startArea` is dereferenced with `!` there because `SpawnWorker()` has already rejected a null one.
- The owner fall-through is deliberate asymmetry, and it is the reason a sandbox needs no catalog: a spawner with no `OwnerId` and a start component with no `FactionCatalog` behave exactly as they did before FEAT-10. Only a map that actually declares factions *and* names an owner can reach the refusal.
- `tests/terrain_faction_assignment_probe.gd` covers the two-spawner case: two spawners owned by `player_1` and `player_2`, two registered `PlayerContextComponent`s on factions `alpha` and `bravo`, over the same four-faction catalog the rest of that probe uses — each worker must land on a cell whose `StartAreaAt` equals its own faction's `StartIndexOf + 1`, and the two must land on different cells. Because `bravo` is locked to start 3 there, the two spawners are not merely in "start 0" and "start 1", which is what makes the check able to fail. **Mutation:** reading `ActiveStartIndex` instead of the owner's start puts both players on one cell.
- `tests/addon_contract_scan.ps1` pins the literal `StartIndexOf(player.FactionId)` in this file under its `# FEAT-10:` block, so the owner-resolution chain cannot quietly revert to the local player's start.
